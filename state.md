## Decision log
*(decision — rationale)*
- **Nothing enters BioMobi's fact tables before a human has seen it on a review surface built for that purpose (2026-09-09)** — the workstream already gated *inclusion* through `DECISION` columns in CSVs. Round 1 of the composition harvest showed that is not enough, because a CSV does not let a reviewer see whether a **number was transcribed correctly**, and every value in that round was read off a source page by a model rather than by a person. So the chain now runs **source → an extraction script that is the transcription of record → generated CSVs → a generated review page → the reviewer's per-row marks and per-object remarks → corrections made at the extraction script → loader**. Two properties make it work rather than decorate: the page is a **pure function of the CSVs**, so it cannot drift from the data and a new round is one command; and a correction is made **at the extraction script, never in the database and never in the page**. Reviewer instruction, in their words: *"ik wil ... overzichtelijk kunnen zien welke bronnen je hebt gevonden, voor welke wastestreams deze compositiewaardes vindt ... zodat ik dit manueel allemaal kan checken."* Generalises beyond composition: the register's 687 unverified claims face exactly this problem on the volume side.
- **A compilation table is an acceptable source, on condition of quality — and a predicted value is carried through, never filtered out (2026-09-09)** — both were open questions that gated eight of round 1's sixteen objects. Feedipedia/feedtables qualifies as a compilation because it is public, resolvable, and every value carries mean, SD, min, max and **n**; the condition binds, so a compilation with no stated sample basis is not the same thing, and compilation-vs-primary stays visible on every row. On predicted values: the source marks equation-derived values with an asterisk, and rather than rule on them in the abstract they are extracted with `predicted = yes` and judged per case in review — *"het is niet zwart-wit"*, and a predicted NDF on 241 samples is not the same proposition as a predicted gross energy on 2. **What the column actually prevents is a predicted value entering silently.** This bounds, without reversing, the 2a finding that secondhand provenance was not worth its curation cost: the difference is that these compilations state their own evidence.
- **The composition parameter catalogue is a vocabulary that GROWS, not a required vector (2026-09-09)** — this settles what the charter's *"single, fixed-shape composition vector"* actually is. **The vector is a model-layer projection over the catalogue; it is not a shape any BioMobi row has to fill.** BioMobi stays sparse: a parameter with no row for a stream means *not measured*, never zero, and is never padded to make a stream look complete. The consequence is the one that matters in practice: **uniformity across streams is not required** — one stream may carry proximate analysis and heavy metals, another only dry matter and pH, and both are correct. The 62-parameter starting core registered on 2026-09-09 was chosen from what composition sources actually report (Weende, Van Soest, sugars, elements, energy, a small physical and microbiological set) and deliberately *not* from any one source's shape — the mistake 2c made when a deliverable's columns dictated BioMobi's facets. **Growth rule: a source reporting something new gets a CSV row and a NEW migration, never a squeeze onto a near-neighbour.** It was exercised the same day, on evidence only: six parameters added because two sources that were actually opened print them, while Phyllis2's ten-oxide ash breakdown was left out because nothing needs it yet. **Grow on a source, never on a plausible-sounding gap.**
- **A composition value attaches to the object whose material was analysed — and where no object exists the answer is a GAP, not a new stream row (2026-09-09)** — the object split of 2026-09-08 exists precisely because a crop's fractions *share no composition*, so letting generic commodity data stand in for a fraction would undo it: potato-peel composition is not potato composition, beet-pulp composition is not sugar-beet composition. The binding half is the second: BioMobi has **no `aardappelschil` object**, so potato-peel literature has nowhere valid to land until **G-10** closes. Registering a stream to hold literature we happen to have found would let the composition harvest dictate stream identity — the same error, in a new direction. Worked example the same day: `zetmeel-reststroom` (Prodcom 106220, *"afvallen van zetmeelfabrieken"*) was **left empty** although starch-industry side-stream composition is abundant, because no source says what that material is (**G-19**) and Flanders' starch industry is mostly *wheat* starch, so the potato-pulp literature is probably the wrong material as well. **The absence of a source is not a licence to pick the nearest one.**
- **A composition gap and a volume gap are different kinds of gap, and a source that closes one need not close the other (2026-09-09)** — **composition is an intrinsic property of the object; volume is not.** So a characterisation of potato haulm from anywhere, of any year, is usable, while a tonnage is only usable if it is Flemish and current. This halves the search space for composition gaps and it is why **F-004** (potato haulm, 744.945 t, no characterisation source anywhere) is raised separately from **F-003** rather than added to it. It also explains the round-1 asymmetry: the *volume* side of the top 10 rests on Flemish monitors that barely exist below sector level, while the *composition* side rests on international databases that describe the same materials well — Phyllis2 and Feedipedia between them cover 14 of 16 objects.
- **The legacy internal Excel is abandoned as a BioMobi input (2026-09-07)** — the old workbook demanded per-row human curation to yield ~271 composition measurements of secondhand provenance, and once 2b had delivered a sourced, claim-level corpus that cost stopped being worth paying. Nothing from it was ever loaded into any database. Its loader and manifests were deleted rather than archived, so nobody is tempted to run them; git history keeps them. This **answers the "salvageable existing data" open question in the negative** and withdraws flag F-001. The one result that survives the input: the workbook's own fabricated-value flag and the schema's `source_key NOT NULL` partitioned the 631 rows *identically*, which is the strongest validation the phase-1 provenance design has had.
- **A BioMobi `stream` is an OBJECT — a thing you could put in a bag (2026-09-08, supersedes the 2026-09-07 formulation)** — registering the 80% selection forced the question, because some of the 13 selected commodities bundle physically different materials that share no composition (Suikerbiet = the beet + loof + pulp; Aardappel = the tuber + loof; Kool- en raapzaad = straw + crush meal; Spruiten = the sprout + stalks). So 13 commodities entered as **20 objects**. **If a row's name only makes sense by saying where the material came from, it is not an object.** The first attempt made chain stage part of stream identity and produced `aardappel-industrie`, `aardappel-primair`, `suikerbiet-primair`, `bloemkool-primair`, `spruiten-primair` — none of which is a thing. A potato peel is a potato peel wherever it arises; where it arises is a property of an *observation*, and `supply_observation` already carries geography, year and source for it. This is project-level because `stream.code` is the primary key every fact row and the whole model layer will reference, and because it decides what the fixed-shape composition vector is a vector *of*. It also dissolves the G-08 "incompatible quantities" problem: *oogstresten* and *voedselreststromen* of one crop were never contradictory figures, they were measurements of **different objects**.
- **Classification is a facet of the object, and BioMobi's first facet is the register's commodity ladder (2026-09-08)** — `classification_scheme` names an axis, `classification_term` holds that axis's vocabulary and nests it through `parent_term_id`, `stream_classification` tags objects; a stream is linked to its **deepest** term and the ancestors are reached by walking up, never stored as extra links. The first facet is `bioloop-commodity`, taken straight from the register workbook's own `l2`/`l3` levels (4 branches, 7 subgroups). **Chain stage is explicitly not a facet.** This closes the standing "controlled vocabulary / classification of streams" question for now — deliberately cheaply, on a vocabulary that already survived eight sources — and leaves EWC to enter later as a *second* scheme, which is `INSERT`s rather than a migration. An earlier attempt loaded `bioloop-tak` + `bioloop-keten` instead, chosen because they were the columns the register's deliverable happened to expose; letting the input's shape dictate the data layer's shape was the error.
- **The register's tonnages are not summable across the split (2026-09-07)** — the 80/20 arithmetic runs at commodity level (the largest figure any one source gives a commodity), so adding up the split streams produces a different and unsupported quantity. There is **one derivation, and it lives in the register**: a second implementation inside the loader disagreed with `derive.js` on Aardappel (429.871 vs 548.305, because OVAM's *voedselverlies* and *nevenstroom* are additive components there) and was removed rather than reconciled. Generalises: a downstream consumer of the register reads its numbers, it does not recompute them.
- **Project treated as semi-reset; charter is the source of truth, proposal is background only** — first ~18 months drifted, MooV underdelivered, staff turnover; proposal goals valid but methods/timeline unreliable.
- **Build BioMobi from scratch in PostgreSQL (+ PostGIS), not the old Excel** — old internal data was inconsistent in variables, format and sourcing; need standardisation, value-level provenance, extensibility, native spatial support.
- **Three-layer architecture — BioMobi (data) / transport + process-application (rules & transformations) / model (engine)** — keeps the data layer model-independent and reusable; isolates all model-coupling in the rule layers.
- **"Application" = "process" (one database; endpoint vs middle-step framing)** — both are constraint + transformation objects; only the role differs.
- **Model is logistics-first; phase 1 is screening, not chaining** — for a single biomass, screen technically possible applications (apply their criteria), then filter by transport feasibility. Chaining (cascading) and optimisation only enter with multiple applications/biomasses and circularity. Build the individual steps first, layer chaining/optimisation on top later.
- **Composition is one fixed-shape vector, shared by streams and process outputs (SETTLED)** — a process/application takes the composition vector, transforms the values, returns a vector of the same shape; this is what enables cascading. BioMobi's composition schema is the canonical representation for raw streams and intermediates alike.
- **Multiple biomasses and cascading are built in parallel, then joined (SETTLED)** — each is a self-contained extension of the linear baseline; solve them independently, then integrate into a combined model. Cleaner than forcing a sequential order. (Supersedes the earlier streams-vs-applications ordering question.)
- **Variable-resolution capture; resolution/basis recorded per value; model accepts mixed granularity** — available data will be uneven (monthly vs annual); the system adapts to the data rather than demanding uniform resolution.
- **Regulatory, transport-feasibility, processing rules and demand-side specs excluded from BioMobi** — these are rules/transformations, not stream facts.
- **Backbone = one git repo, layered (charter / state / protocol / flags + per-workstream hubs); sessions run in Claude Code and write back directly** — durable, portable single source of truth; memory lives in the repo, sessions are disposable surfaces onto it; hand-offs are automated commits, not manual paste. (Supersedes the earlier "manual vs pipeline hand-off — deferred" open question.)
- **Reference vocabulary ships as a generated data migration, facts do not (2026-09-08)** — the stream/classification rows a sub-project settles are emitted as an `ON CONFLICT`-guarded migration under `database/supabase/migrations/`, so `supabase db reset` reproduces the whole database from git and `db push` is the only route to live. The loader that produced them is the *generator*, not a second way in. Facts (`property_measurement`, `supply_observation`) stay with their loaders, because they carry per-row curation and provenance that a migration cannot gate. A generated migration is never hand-edited and never re-edited once applied — when the selection changes, emit a new one; `ON CONFLICT` makes them stack. First one: `20260908143000_bioloop_streams_selection.sql`.
- **Database hosted on Supabase; the committed migration set is canonical — there is no separate `schema.sql` (REFINED 2026-07-27)** — phase 1 baselined the existing live structure as the first migration under `database/supabase/migrations/`, and a local `db reset` reproduced it schema-identically. A parallel `schema.sql` would be a second source of truth needing manual sync, so it is deliberately not kept: to read the schema, read the migrations or rebuild locally. The live instance stays downstream — evolve it forward via committed migrations, never by editing it directly. (Supersedes the earlier "baseline it into `schema.sql`" formulation; the charter's "schema as version-controlled SQL" still holds, the SQL just lives in migrations.)
- **Raw source data is not versioned (2026-07-28)** — `**/data/raw/` is gitignored across the repo. Inputs stay out of git; the committed ingestion script plus the human-verified curation manifests carry the audit trail instead. Applies to the coming OVAM/MONBIO PDFs and literature exports too, not just the database workstream. Trade-off accepted: a fresh clone cannot re-run an ingestion without separately obtaining the input.
- **Ingestion is gated on explicit human curation, not model judgement (2026-07-28)** — each source's crosswalk CSV carries an LLM proposal beside a human `include`/`exclude` decision, per stream *and* per source; the loader refuses to run while any decision is blank. Extends the existing "LLM-proposed, human-verified" crosswalk rule from name-mapping to inclusion.
- **The 80/20 rule applies to prospective harvesting, not to data already in hand (2026-07-28)** — for small, already-collected datasets, selection is manual per stream: check the name (to exclude out-of-scope material) and the source (to validate the entry). Refines, and bounds, the charter's "stream selection guided by the 80/20 principle". Partially answers the "salvageable existing data" open question below.
- **The candidate register covers the supply side of the agri-food chain only (2026-08-15)** — in: primary production (land + sea), auctions / producer organisations, processing industry, retail & wholesale. Out: horeca, catering, households, and anything downstream of retail. An aggregate figure is usable only if every chain stage it spans is in scope, which is why no whole-chain grand total is captured. This bounds what BioMobi's volume side will eventually hold, so it refines the charter's scope rather than merely implementing it. Enforced in `database/register/dictionaries/chain_L2.csv` (`in_scope` column).
- **A single crop is never a commodity subgroup (L3) in the register hierarchy (2026-08-15)** — the seed tree had put `Aardappelen` and `Suikerbieten` at L3 while the same dictionary listed `Aardappel` as an L4 example. Akkerbouw now carries genuine subgroups (`Granen`, `Aardappelen en knolgewassen`, `Suikerbieten en nijverheidsgewassen`, `Peulvruchten en eiwitgewassen`, `Voedergewassen`) with the crop at L4, so the L3 pivot means the same thing on every branch. Recorded here because `commodity_hierarchy.md` requires rule changes to be logged at project level; the member lists themselves stay in the dictionary.
- **The register captures arising volumes only, and excludes manure (2026-08-16)** — settled on the first non-OVAM source (MONBIO 4.0), which reports every stream as productie / import / export / *aanbod*. Only **productie** is a quantity of material arising in Flanders; import and export are trade flows and *aanbod* (production + import − export) is a source-computed derivation, so neither is a claim. Separately, the charter/hub exclusion of **manure and OFMSW** is treated as binding on the register, not only on BioMobi — this removed ~23,4 Mton of 2021 animal side stream in one stroke, which is large enough to be a project-level fact rather than a workstream detail. Both are recorded per-tonnage in `database/register/log.md` so either can be reversed without re-reading the PDF.
- **A source's own residual vocabulary is mapped, never assumed to match ours (2026-08-16)** — MONBIO splits residuals into `nevenstroom` / `productieresidu` on an **economic** axis (has value / has none), whereas `quantity_type.csv` splits on **edible / inedible**. Same words, different meanings, so both MONBIO terms map to `agri-food waste` with `type_assumed = TRUE` rather than to the register's `nevenstroom`. Generalises: when a source's term collides with a dictionary term, check the source's *definition* before mapping. Recorded here because it changes how every remaining monitor source is read.
- **A coverage percentage is only evidence when the row it sits on could have been covered (2026-09-09)** — an aggregate that spans two parents or two levels is *unallocatable by design*: nothing is ever measured against it, so its 0% is a property of the commodity ladder, not of the data. `C-094` (aardappelen + groenten + fruit, 621.063 t) mixes an L4 with two L3s across two L2 groups, and part of its mass is reachable in another branch entirely. The first derived gap list used exactly these rows to name its largest gap and summed them against it, which compares an artefact with a measurement. They stay visible — they are the only thing that names aardappelverwerking, the top target of the source hunt — but as labelled context that is never summed. **Before reading a coverage figure as evidence, check whether that row was placeable at all.**
- **A reported total can be resolved by its siblings, not only by its children — and "unallocated" is not one state but two (2026-09-08)** — the register's derivation scores an aggregate against the rows *beneath* it, so a total that is exactly the sum of the claims *beside* it reads as "nothing explains this". `C-043` (548.305 t) is precisely `C-005` + `C-042` and scored 0%; eleven aggregates were mis-read that way. Separately, a row the derivation *could not place* and a row the registry *deliberately shelved* both surfaced as "no row in the tree" — and the two largest rows in the corpus that look like gaps (`C-532`/`C-342`, perskoeken, 1,35 / 1,02 Mt) are the shelved kind, where promoting them would double-count. Recorded at project level because it is a rule about reading any coverage figure, not a register detail: **before calling a total unexplained, check its siblings and check whether someone already decided to park it.**
- **The 2023 unharvested-potato figure makes every "parts exceed the total" flag in the register, and it is an artefact of averaging (2026-09-08)** — the wet 2023 autumn left 308.000 t of potatoes unharvested, and OVAM reports its totals both incl. and excl. that post. The register's registry treats the pair as *variants* and averages them, so the akkerbouw denominator becomes 423.389 t — a number no source printed — while the children sum to exactly the incl. figure of 577.389 t. Twelve rows and 5,99 Mt read as over-covered when they are at 100%. **Two figures that differ by scope are not two measurements of one quantity.** Settled 2026-09-09: the **incl.** reading is the basis, because the unharvested potatoes sit in the tree as their own component, so the total that includes them is just the sum of the parts; the four excl. totals are parked and steer nothing. Twelve flagged rows became two, and those two are over by *exactly* 308.000 t because they are `ingezameld` figures and unharvested potatoes were never collected. The register's own machinery could not deliver the alternative — keeping the 308.000 t as a selectable stream *outside* the sum — because a component row that stays in the commodity tree always rolls up, and an unallocated row is not selectable. Generalises to any source that publishes one total under two definitions.
- **A source's sub-sector row is not the commodity, and must never occupy its L4 slot (2026-09-08)** — OVAM's *Zuivel* figure (123.219 t) is one of eight NACE sub-sector rows in a single table, beside *Bakkerij* and *Dranken*; MONBIO states plainly that the sector's residuals are melkwei and zuiveringsslib while the milk itself is its production. It had been placed on `L4 = Melk`, so one node **added 12.378 t of farm milk to 123.219 t of factory residue** and the selection ranked the sum at #14. Its seven sibling rows were left above L4 — when one row of a family of eight is treated differently, that is the defect. Now split into two materials: `Melk` for milk, `Zuivelnevenstroom` for dairy-processing residue. Recorded at project level because it is a rule about how *any* source's sector figures enter the commodity ladder, and because it moved a stream out of the top 20.
- **A figure skipped under the restatement rule is only safe if its owner will actually be extracted (2026-09-08)** — melkwei, 49.722 t, is printed in a table in both extracted MONBIO editions and was correctly assigned to S005 (MONBIO 1.0), which owns the 2018 estimate. **S005 is retired.** So the figure landed nowhere, and the gap record called whey *"absent from all 801 claims"* and sent the literature workstream hunting a new source for something two sources on disk already measured. Captured as C-802/C-803 by reviewer decision, as a narrow exception (the zuivel cell only, never the whole table). Generalises: **before recording anything as absent, check that the owner named by the skip is a source that will be read.** The same check applies to a gap's stated mechanism — whey was the example for "no Prodcom code, so the monitor cannot see it", yet Prodcom 105155 exists and is merely *confidential*, which needs the opposite response.
- **The 80/20 selection is made on the candidate register, not on BioMobi, and it is now made (2026-09-04)** — the charter asks for stream selection "guided by the 80/20 principle", which cannot be done inside a database that does not yet hold volumes. It was therefore done on a standalone claim-level corpus first: **69 selectable streams, an envelope of 7.301.257 t/yr, 80% at 13 streams and 90% at 20** (figures after the 2026-09-08 control; the top-13 list is unchanged from the 2026-09-04 close). This is the answer to that success criterion and it decides which `stream` rows BioMobi registers first. It is a **prioritisation sort, not a hard gate** — a stream outside the top 13 is not excluded, it is simply not first. Reproducible from the workbook with `database/register/tools/select_streams.js`.
- **A stream's volume is the largest figure any *one* source gives it — never a sum, never a mean across sources (2026-09-03)** — summing double-counts the same material, and averaging rewards ubiquity over mass (it once ranked a 1.783 t stream above a 681.000 t one, because sources that never measured it were counted as zeros the register's own "absence = not measured" invariant says do not exist). Recorded at project level because it is the rule by which the stream list was chosen, and any later revision of that list must use the same one.
- **MONBIO and OVAM figures must never be summed, and the two cannot cross-check each other (2026-09-01)** — on the same year 2020 MONBIO reads 5.499.135 t against OVAM's 2.583.633 t (2,1x overall; akkerbouw 24x, vee 5,4x, vis 38x), because MONBIO counts *productieresiduen* and OVAM only food-linked *voedselreststromen*. Ten of the thirteen selected streams are straw, leaf, pulp and stalk — outside OVAM's scope by construction. This bounds what any later validation of BioMobi's volume side can claim.
- **Data gaps split into two kinds needing opposite responses (2026-09-03)** — *class A*: the figure is in the corpus but the selection cannot see it (wrong level, wrong marker, wrong parent) — **no new source helps**, and it is fixed by a placement decision; *class B*: nothing measures it — **only a new source helps**. The first coverage audit reported one 2 Mt "food industry has no detail" gap that was in fact both. Generalises beyond the register: before commissioning data, establish which kind of gap it is.
- **A source is screened by how it carves, not by its title (2026-09-03)** — MONBIO's food-industry residual detail is exactly the set of Prodcom codes that happen to name a by-product, so a stream with no such code is invisible to it however large; OVAM publishes the food industry at subgroup level and nothing finer. **A candidate source that carves by NACE class, by Prodcom code, or by a monitor's own loss definition will reproduce the gaps we already have. The useful question is: does it carve by *process*?** This is the screening rule for the whole remaining source hunt (F-003), in every workstream.
- **Checked-and-empty is recorded, never discarded (2026-08-15 →, formalised through 2026-09-04)** — a source read cover-to-cover that yields nothing keeps its row, its archived PDF and a full account in the log of every figure refused and why. Two of the register's eight sources are zero-yield. Without this, "not checked" and "checked and there is nothing there" are indistinguishable, and the same PDF gets re-read.
- **Solo for now; do not design for future collaborators** — keep overhead low; revisit if the team grows.
- **Tooling** — PostgreSQL + PostGIS on Supabase, version-controlled SQL, Python/pandas ingestion; Zotero (refs) + Obsidian (notes, linked by citation key); literature-derived values flow into BioMobi carrying their citation key as provenance.
